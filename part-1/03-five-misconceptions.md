# 第 3 章 AI 应用的设计原则与常见误区

架构方案确定以后，开发者仍然可能在实现中混淆几个相似的概念：模型给出了理由，是否就能说明结论可靠？系统保存了对话，是否就具备任务恢复能力？工具参数通过校验，是否就可以执行？

这些误解往往不会在第一次演示中暴露。演示使用完整材料、运行在单进程中，也没有真正危险的外部动作。当应用开始处理缺失数据、并发请求和生产权限时，原先含混的概念就会变成具体的错误。

本章建立一组供后续实现使用的设计原则。原则中的机制说明尽量给出可核查依据；具体取舍则说明适用条件。它们用于帮助读者提出正确的问题，不构成无需验证的成功配方。

## 3.1 用任务结果评价能力

一份报告条理清楚、措辞专业，说明它具有良好的表达形式。它是否帮助用户完成任务，还需要其他证据。

在告警案例中，模型可能准确复述指标，却把发布时间与异常时间接近解释为已经确认的因果关系。这样的报告表面完整，但关键判断错误。相反，一份简短报告如果清楚列出事实和信息缺口，可能更适合当前调查阶段。

因此，评价对象应该从“回答看起来怎么样”转向“任务要求是否被满足”。第 2 章定义业务成功标准，第 5 章再把它拆解为可执行检查与内容评审。

### 将完成状态与正确性分开

请求成功、报告通过结构校验、内容通过评审，是三个不同的结果。记录时应保留它们各自的状态，否则团队难以判断到底改善了什么。

例如，修正输出 Schema 可能提高结构通过率，却没有改变事实错误；补充材料可能改善事实质量，却增加等待时间。把这些变化合成一个模糊的“智能程度”，会掩盖可以定位和改进的问题。

对于开放式任务，可以先定义若干关键检查项，不必立即构造一个总分。检查项是否合理、评审者能否一致使用，也需要通过样例讨论确认。

### 早期样例用于发现问题，不用于夸大结论

项目初期应尽早保留正常与失败样例。它们帮助团队发现遗漏的字段、含混的提示和不合理的流程，但少量样例通过不能证明系统已经适用于所有业务输入。

为了比较方案，可以将部分样例用于开发，把另一些保留到阶段性评价时再使用。如果不断根据保留样例修改提示，它们就已经参与方案选择，后续评价应承认这种影响，必要时补充新的样例。

scikit-learn 官方文档解释了测试数据参与模型选择会使效果估计过于乐观的问题。本书借用这一评估原则，提出对提示与应用方案也要区分开发材料和评价材料；这是一项方法上的应用，并不意味着提示修改等同于模型参数训练。[Common pitfalls：Data leakage](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)

在故障案例中，样例划分还应注意事件关联。同一次事故的多个近似片段如果分散到开发与评价材料中，可能无法充分检验系统对新事故的适应能力。划分方式应围绕准备评价的泛化目标决定。

## 3.2 为知识与判断标明证据地位

AI 应用经常需要在材料不完整时提供帮助。严谨的做法是区分已知事实、待验证假设与无法判断的部分，而不是要求模型对所有问题都给出确定答案。

以“错误率上升发生在发布之后”为例：如果时间记录可靠，可以确认观察到的先后顺序；如果没有版本对照与其他调查材料，就不能由此确认发布是原因。这是证据能够支持的结论范围不同，不是换一种语气就能补足信息。

产品展示也应保留这种区分。观察、假设、建议和执行结果如果都出现在一个没有标签的摘要框里，用户容易把它们当作同等可靠的信息。

### 解释文字不是独立验证

让模型解释结论可能有助于人发现问题，但解释本身仍然是生成内容。它不能自动充当支持结论的独立证据。

Turpin 等人在 2023 年的研究中发现，在其测试的模型与任务上，思维链解释可能没有如实反映影响答案的因素。这个结果支持我们避免把生成的解释直接当作完整因果审计记录；它不意味着所有解释都无用，也不能据此外推所有当前模型的具体错误率。[Language Models Don't Always Say What They Think](https://arxiv.org/abs/2305.04388)

对于业务审阅，更有操作价值的材料包括：模型实际获得了哪些输入，结论引用了哪些记录，执行器真实调用了什么，以及外部系统返回了什么。这些材料仍需检查来源与完整性，但至少可以逐项核对。

本书因此要求保存可审计的外部过程，而不要求把模型生成的完整推理文字作为系统恢复或授权依据。

### 不把自报置信度直接解释为正确概率

如果模型写出“置信度 90%”，应用还需要知道这个数字怎样产生、针对什么事件，以及是否在相关数据上经过校准。单次生成的数字不能自行证明“类似回答中有 90% 正确”。

对第一版告警助手，直接呈现证据、假设和信息缺口，更容易让使用者理解判断依据。若以后确实需要概率预测，应先定义预测事件、观测结果与评价方法，再讨论数值是否适合用于决策。

这个原则并不禁止应用表达不确定性。它要求表达方式与能够提供的证据相称。

## 3.3 区分上下文、应用记忆、任务状态与 KV Cache

“记忆”在不同系统中可能指不同东西。如果不先区分层次，开发者可能用错误的组件解决问题，例如试图用推理缓存保存审批结果，或者用聊天摘要恢复外部操作。

本书采用以下工作定义。框架可能使用不同名称，阅读其文档时应按职责核对，而不是只按名词对应。

| 概念 | 本书讨论的职责 | 告警案例中的例子 | 不能由名称推断的能力 |
| --- | --- | --- | --- |
| 上下文 | 本次模型调用可以使用的输入信息 | 指令、证据、必要的历史内容 | 材料一定完整、正确或得到充分利用 |
| 应用记忆 | 应用为未来任务保留并按需取用的信息 | 已确认的服务说明、用户偏好 | 自动跨会话准确、永不过期 |
| 任务状态 | 应用推进任务所依据的显式记录 | 任务阶段、待审批动作、版本与执行结果 | 写入存储就自动获得一致性和恢复保证 |
| KV Cache | 某类模型推理中的中间计算复用 | 已处理 Token 的注意力键和值 | 业务事实存储、授权或工作流恢复 |

### 上下文是为当前调用选择的信息

应用可以将数据库中的材料、历史消息和外部查询结果组织成一次模型输入。模型服务也可能提供会话等机制，帮助保存或组织历史。使用这些能力时，仍需理解究竟哪些信息参与了当前生成。

把更多历史留在系统中，不等于当前模型一定获得了全部历史；即使获得了，也不等于每项信息都会被正确使用。第 7 章将讨论选择、压缩和追溯，而不是将上下文长度本身作为质量目标。

### 应用记忆是一种数据管理职责

应用记忆可以存放在关系数据库、文档系统、键值存储或其他合适的载体中。是否需要向量检索，取决于如何查找这些信息，不能从“记忆”两个字直接得出。

如果保存“某服务常见故障与处置记录”，还需要区分已确认经验与模型提出的假设，并记录来源、适用版本和更新时间。否则，一次错误推断就可能在后续任务中反复出现，被误当成历史事实。

因此，记忆设计需要回答写入条件、读取权限、更新与失效规则。这些要求来自应用对数据的使用方式，而不是模型自动获得的能力。

### KV Cache 解决的是计算复用

在常见的自回归 Transformer 推理中，KV Cache 保存已经计算出的注意力键和值，以减少后续生成中的重复计算。Hugging Face 的官方文档说明了这一机制及不同缓存实现。[How caching works](https://huggingface.co/docs/transformers/cache_explanation)

它与“保存一条用户偏好”处于不同抽象层。推理系统可以按照实现条件复用、迁移或保留缓存，所以也不能简单断言 KV Cache 必然只存在于单次请求中。但无论如何，缓存本身没有定义业务记录的授权、更新和任务恢复语义，不能据此替代应用数据库。

应用层的回答缓存又是另一个概念：它保存既有结果以供复用，需要判断请求是否等价、数据是否过期以及当前用户是否有权使用该结果。不要把几种不同目的的缓存混为一谈。

## 3.4 让任务状态表达可执行的事实

设想一个调查任务已经生成处置建议，正在等待值班人员批准。此时进程退出，新的进程需要接着处理。

如果系统只保存“建议回滚，等待用户确认”这句消息，新进程仍然不知道需要回滚哪个资源、批准的是哪个版本、批准是否已经过期，以及操作是否可能已经发出。

恢复所需的信息不只是会话内容，而是对业务有明确含义的状态。

### 状态包含身份、阶段与待执行内容

下面是状态设计示意，不是可直接接入的协议，也不是第 5 章离线示例已经实现的功能：

```text
任务标识：investigation-demo-001
当前阶段：等待审批
资源标识：payment-api / 测试环境
候选动作：将指定发布回滚到已记录的目标版本
动作版本：3
审批状态：尚未批准
执行状态：尚未发送
状态版本：7
```

这些字段为系统提供了可检查的条件：审批是否针对当前动作，任务是否仍在可执行阶段，以及有没有别的执行器已经推进了状态。字段名称和存储形式可以变化，但需要表达的事实不能靠猜测补全。

在第 5 章的只读应用中，持久化审批状态并非必要，因为它没有这样的业务过程。本节提前介绍状态边界，是为了避免读者在后续增加能力时继续只依赖文本历史。

### 消息可以参与状态系统，但不能省略状态语义

说“聊天历史不能做状态”，如果理解成绝对禁止，也不准确。一个系统可以把带类型、标识、版本和转换规则的事件作为事实来源，再从事件重建当前状态。部分事件也可能包含消息内容。

关键区别在于：普通自然语言对话并未自行定义事务、并发、审批绑定和恢复规则。如果系统为事件补齐这些规则，可靠性来自这些明确机制，而不是来自“记录了聊天”。

同样，数据库中有一行 JSON，也不意味着状态设计已经正确。还需要规定哪些主体能够更新、如何处理并发，以及一个状态变化怎样与外部动作关联。

### 从状态生成上下文，保留返回边界

任务状态可以提供给模型需要了解的部分，例如已知事实、当前目标和允许的候选动作。模型返回的建议则先经过校验和策略判断，再由应用更新状态。

这是一种适合本书案例的设计方向。它让模型参与推理，又避免模型仅凭一段文本把任务改成“已批准”或“已完成”。第 10 章将进一步讨论状态转换与并发控制。

## 3.5 将内容约束、业务校验与授权分开

模型输出可以在某一层有效，同时在另一层无效。将这些层次混在一起，是产生错误执行的重要原因。

| 检查层次 | 例子 | 能回答的问题 |
| --- | --- | --- |
| 格式 | 工具名和参数能够被解析 | 这份数据能否被程序读取？ |
| 业务合法性 | 资源存在，参数组合符合接口规则 | 这项请求是否满足业务约定？ |
| 证据支持 | 所引用记录确实支持调查结论 | 这个判断是否有相应依据？ |
| 授权与策略 | 当前主体有权限，动作满足审批条件 | 系统是否允许执行？ |
| 执行结果 | 外部系统返回可核对的结果 | 动作实际发生了什么？ |

不是每个场景都能自动检查全部层次。需要人工判断的部分应当明确保留，而不是用一个“验证通过”字段模糊覆盖。

### 提示不能代替授权

提示可以告诉模型“不要修改生产资源”，但如果执行器仍然允许任何参数通过，并使用具有修改权限的凭证，系统就缺少独立的执行限制。

OWASP 的提示注入防护资料建议在模型之外保留授权与最小权限控制，并针对工具与会话上下文校验调用。本书据此将模型内容引导与执行权限分开讨论。[LLM Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

例如，只有只读凭证的指标查询工具，即使接到不符合任务的修改建议，也不应有路径把建议转换成写操作。反过来，如果工具实际提供了通用脚本执行能力，仅把名称写成“查询工具”不会使它变为只读。

权限边界需要覆盖真实执行能力。它仍然依赖代码、凭证和基础设施的正确配置，不能被描述为不存在实现缺陷的绝对保证。

### 人工审批应当绑定具体动作

“人已经点过同意”本身还不足以说明当前动作获得授权。如果批准后模型更换了目标资源或修改了参数，原来的审批未必适用。

在需要审批的设计中，应将批准记录与具体动作、资源、参数版本和适用条件绑定。执行前再检查这些条件是否仍然成立；如果发生影响决策的变化，应重新判断是否需要审批。

这是本书对案例流程的设计要求，不意味着每个模型调用都必须人工确认。是否审批应根据动作性质、现有业务规则与可接受风险决定，普通只读整理不应机械套用高风险写操作的流程。

## 3.6 不把恢复能力简化为“保存并重试”

保存任务状态有助于知道系统走到了哪里，但外部操作可能在状态写入之前或之后发生。理解这个时间差，是设计恢复机制的前提。

考虑一段时间顺序：

```text
应用发出创建工单请求
        ↓
工单系统已创建记录
        ↓
响应在网络中丢失
        ↓
应用观察到超时
```

如果应用恢复后直接重新创建工单，就可能产生重复记录。如果直接把任务标记为失败，又可能漏掉实际已经创建的工单。

### 幂等依赖具体契约

调用方可以使用稳定的操作标识，让支持该约定的服务识别同一次业务操作的重试。但“增加一个幂等键字段”并不会自动实现幂等：服务端需要实际处理重复请求，并定义参数变化、记录保留期与结果返回方式。相关工程讨论见 AWS 的[幂等 API 设计文章](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)。

对本书的工单例子，应先确认工单服务支持怎样的操作标识与结果查询。如果无法判断先前动作是否生效，合理的恢复状态可能是“结果待核对”，而不是盲目重试。

幂等也不等于所有响应内容逐字相同；核心是同一业务操作的重复请求不会造成额外的预期副作用，具体保证仍以接口约定为准。相同参数的两次请求也可能是两个独立业务意图，不能只按参数相同就随意合并。

### 检查点与外部动作不天然构成一个事务

检查点（Checkpoint）记录应用可恢复的进度。如果检查点存储与外部服务不属于同一个受协调的事务边界，仅保存检查点就不能保证外部动作恰好执行一次。

因此，后续章节会分别讨论状态持久化、动作标识、执行结果核对与恢复路径，而不使用“支持 Checkpoint，所以不会重复执行”这样的推导。

对于只生成草稿的第一版应用，重复调用主要带来资源消耗和不同结果；对于创建记录或修改资源的应用，重复动作还可能改变业务状态。恢复策略必须随着副作用改变。

## 3.7 用问题诊断决定增加哪种能力

当应用效果不好时，增加组件是一种可能的改进方式，但应先定位失败发生在哪一层。

下面列出本书案例中的几种诊断方向。它们是候选措施，需要用对应样例验证，不表示引入后必然改善。

| 观察到的问题 | 首先检查什么 | 可以评估的调整 |
| --- | --- | --- |
| 关键材料根本没有进入输入 | 数据接入与权限 | 固定查询、检索或调用方补充 |
| 材料已在输入中但经常被遗漏 | 输入组织与任务说明 | 重新组织上下文，拆分过多目标 |
| 输出结构不符合约定 | 接口能力与契约 | 结构化输出、应用校验与清楚的失败处理 |
| 查询步骤确实取决于中间证据 | 控制流程与工具反馈 | 在受限范围内引入动态调查 |
| 相同外部动作重复发生 | 调度、状态与副作用管理 | 操作标识、并发控制与结果核对 |
| 多个角色反复讨论却没有新证据 | 协作职责与终止条件 | 简化流程，明确交付物与证据来源 |

例如，知识检索可以为回答提供外部材料，但不能仅凭“检索到了文档”就确认答案正确。材料可能过期或不适用，模型也可能误读材料。增加检索后，应分别评价材料获取和内容生成。

同样，多智能体协作是否有价值，需要看任务分工、上下文与权限边界。多个模型给出一致回答，不能自动视为多份独立证据；它们可能使用相同材料或重复相同错误。未经验证，不应按独立事件的假设计算所谓一致性置信度。

### 简单不是目的，复杂也不是能力证明

有些场景确实需要持久化工作流、多个角色或复杂检索。为了减少组件而忽略必要的权限隔离与恢复机制，也是一种错误简化。

更好的问题是：这个组件解决了哪一种已经明确的问题？增加了什么新的失败方式？我们用什么样例判断它值得保留？

比较应尽量控制输入、任务标准和运行条件。若模型、提示、检索与评测材料同时变化，即使结果改善，也很难判断是哪一项变化起了作用。可以记录组合方案的整体效果，但不要把收益无依据地归因到单一组件。

## 3.8 建立可核查的改进记录

随着应用演进，最容易丢失的是结论适用的条件。一句“新方案更准确”，如果没有任务集、版本、评价方法与失败样例，就很难指导下一次修改。

建议为每次重要变化保留一份简短记录：当前问题、做出的修改、使用的输入与版本、验证方法、观察结果，以及尚未覆盖的条件。

对第 5 章的离线示例，这份记录只能说明：在指定环境下，保存响应通过了哪些业务边界检查。它不能说明在线模型能够稳定产出同样内容，也不能提供真实模型的延迟、成本或准确率。

同样的要求也适用于本书中的实验和示例。教学构造用于解释机制，设计建议用于指导取舍，真实实验结果则必须有对应记录。三者应在文字中明确区分。

## 本章小结

AI 应用设计需要保持几组边界清楚：任务结果与表达质量、事实与假设、上下文与持久化状态、格式校验与执行授权，以及进度恢复与外部副作用。

这些边界帮助我们把可由程序保证的性质写成规则，把需要实验判断的效果放进评测，把尚不充分的证据保留为信息缺口。接下来的第 4、5 章将从一次受控模型调用开始，实现其中最小但完整的一部分。

## 思考与练习

1. 把一个现有聊天应用中的数据分别归入上下文、应用记忆和任务状态。哪些数据目前没有明确的更新与失效规则？
2. 某个接口请求超时，但外部动作可能已经完成。你需要哪些记录与查询能力，才能决定是否重试？
3. 两个模型都给出了相同结论，但引用同一份过期材料。这种一致性能说明什么，不能说明什么？
4. 为“检索已经改善应用”设计一个可检查的论证：应该记录哪些材料、评价哪些阶段，以及保留哪些反例？

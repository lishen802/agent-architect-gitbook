# 第 2 章 从需求到方案：智能体应用的架构决策

> **已有经验**：需求拆解、架构评审与 ADR。
>
> **新增问题**：控制方式、信息获取和动作权限需要分别决定。
>
> **本章产出**：一份标准一页方案和可推翻当前选择的验证计划。

“我们想做一个 AI Agent，自动处理线上告警。”

这是一个常见的项目起点，但还不是一份可以直接实施的需求。它指定了技术名称和大致场景，却没有说明要代替哪一部分工作、允许系统做什么，以及怎样判断任务已经完成。

如果立刻开始选择框架，团队很容易把大量精力放在运行时、工具协议和多智能体协作上，最后才发现：值班人员最需要的只是把分散材料整理到一起；或者，真正阻碍自动化的是数据权限与审批流程，模型能力并不是首要问题。

本章讨论如何从业务问题推导架构：先把技术诉求翻译成业务任务（2.1），在方案之前写下成功标准（2.2），选择控制方式（2.3），用标准一页方案记录判断（2.4），标明数据与动作边界（2.5），检查反馈与退出机制（2.6），估算资源预算（2.7），识别不值得引入模型的职责（2.8），再用架构决策记录保留推理依据（2.9），最后把结论变成下一步实验（2.10）。

**本章示例说明**：本章继续使用运维助手案例。案例、比较表和 ADR 都是设计分析与教学构造，不是已经完成的生产项目复盘。读完本章，你应当能够写出一份有边界、有备选方案、有验证方法的架构决策记录。

## 2.1 把技术诉求翻译成业务任务

**要解决的问题**：一句“做一个 Agent”背后，到底要完成哪些工作？

“自动处理告警”至少可能包含五类工作：接收并去重告警、收集材料、解释现象、提出处置建议，以及执行操作并验证恢复。它们需要的信息、承担的风险和适合的实现方式并不相同。

因此，需求讨论应先把任务拆开，而不是把整条流程交给一个宽泛的目标。

| 工作环节 | 预期交付物 | 需要进一步确认的问题 |
| --- | --- | --- |
| 接收与去重 | 一条可追踪的调查任务 | 哪些告警属于同一事件，如何处理重复通知？ |
| 材料收集 | 带来源与时间的证据包 | 数据在哪里，调用者是否有权访问？ |
| 现象解释 | 事实、假设与信息缺口 | 结论需要达到什么可信程度，由谁审阅？ |
| 处置建议 | 候选动作与适用条件 | 有无既有操作手册，哪些建议需要审批？ |
| 执行与验证 | 操作记录及结果判定 | 如何授权、避免重复执行，以及确认状态变化？ |

这张表用来先区分责任，再选择实现；每个环节是否独立部署，是后面才需要决定的事。

### 明确使用者与使用时点

同样一份分析，在不同工作阶段有不同用途。故障调查初期，值班人员需要快速了解已知事实与信息缺口；事故复盘阶段，则需要完整时间线和经过确认的原因。前者可以包含明确标注的假设，后者不能把未经验证的猜测当作最终结论。

对于本书的第一版应用，我们选择较小的任务：在告警出现后，把调用方已经提供的材料整理成一份可审阅草稿。用户仍负责调查和处置，系统不自动关闭告警。

这样得到的需求描述可以写成：

> 当值班人员提供一条告警及相关证据时，系统整理主要现象、证据支持的调查假设和待确认事项；每项发现能够回到输入材料，信息不足时明确说明。输出用于辅助人工调查，不作为自动执行操作的依据。

这段话包含触发条件、输入、交付物与使用边界。它没有预先要求使用智能体，因为目前尚未证明需要模型自主选择下一步。

### 区分事实、假设与约束

需求文档里的每一句话并不具有相同的证据地位。

“现有告警平台能够提供服务标识”可以通过接口检查确认。“模型整理材料能够缩短调查时间”则是待验证的产品假设。“第一版不执行生产写操作”是团队对范围的约定。

如果把三者混在一起，后续设计就容易建立在未经验证的前提上。建议为关键前提留下来源或状态：已经确认、尚待验证、由项目约定。这里的状态用于管理决策依据，不是给业务事实随意添加可信度分数。

## 2.2 把成功标准写在方案之前

**要解决的问题**：怎样判断一个方案值得做？

没有成功标准，架构比较就会退化成技术偏好。一个复杂方案看起来能力更多，却未必改善用户的工作。

先定义交付物是否合格，再定义引入它是否值得。

对告警草稿，交付物标准包括数值不被篡改、观察与假设分开、引用与材料对应、信息缺口清楚。业务价值则要通过使用过程判断：值班人员是否更快找到关键材料，是否减少重复整理，是否增加了纠正错误的负担。

两类标准应分别记录。模型即使生成了结构合格的报告，也可能只是把原始材料改写一遍，没有减少用户工作量。

### 定义指标的对象与分母

“准确率达到 95%”作为验收描述还不充分。它没有说明被判断的对象是字段、句子、整份报告还是完整任务，也没有说明超时与拒答是否计入。

更明确的定义例如：

> 在满足输入约定并进入评测的任务中，报告通过预先定义的事实、引用和信息缺口检查，并能供值班人员继续调查，记为一次任务通过。调用失败也保留在任务记录中，不因没有产生报告而从分母中消失。

这是适合本案例的一种指标定义，其他应用需要按自己的交付物重新定义。若还需要分析格式质量，可以另外计算生成结果的契约通过率，但应写清它与任务通过率的区别。

同样，衡量耗时时需要明确起止点。模型完成生成的时间，与用户取得一份经过审阅的报告所需时间，回答的是不同问题。前者适合定位技术瓶颈，后者更接近实际使用价值。

### 分开评估不同错误

漏掉一条辅助日志、把错误比例写错一个数量级、向无权限用户展示敏感材料，三者的后果相差很大，应当分别计数。

项目可以根据后果制定不同规则：一般表达问题允许人工修订；关键事实错误会使报告不通过；权限越界则触发单独的阻断与调查流程。具体分类由业务确定，模型打分只能作为辅助。

少量样例中没有出现失败，说明的是在给定样例、版本和条件下发生了什么；未覆盖的场景仍需单独分析。

### 保留一个无需模型的基线

在运维案例中，可以先用固定模板展示指标、发布记录和日志摘要。它不能提出复杂假设，但仍可能解决“材料分散”的主要痛点。

比较模型方案与这个基线，可以回答一个实际问题：生成能力带来的整理与分析收益，是否足以抵消调用资源、等待时间和人工校核成本？在获得数据前，这应当是一项实验目标，而不是需求文档中已经成立的结论。

## 2.3 选择控制方式，而不只选择技术名称

**要解决的问题**：每个环节的下一步，应该由谁决定？

本书按“下一步由谁决定”区分四种控制方式：规则程序、受控模型调用、预定义工作流与受约束的智能体。第 1 章 1.3 节的图 1-2 展示了它们在同一系统中的组合关系，本节给出每种方式的含义与选择条件。四种方式可以在同一系统的不同环节同时出现，它们之间也没有升级顺序。

Anthropic 的工程文章区分了由预定义代码路径组织的工作流，以及由模型动态决定过程与工具使用的智能体。本书借用其中“由谁决定下一步”的视角，但不将其视为全行业唯一的术语定义。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

### 规则程序：用已知规则处理问题

如果任务可以用稳定规则表达，规则程序通常值得作为首个候选。告警去重、按权限过滤资源和检查必填字段，都可以先从明确的业务规则出发。

“规则明确”指业务判断的规则已经由开发者表达，系统无须让模型临时解释这条规则。程序本身仍会受网络、并发、实现缺陷和外部数据变化的影响。

### 受控模型调用：在固定位置完成理解与生成

如果输入已经给定，只需完成分类、抽取、摘要或受约束的内容生成，可以把模型放进一个普通应用流程。流程仍由业务代码控制，模型只承担其中一个步骤。

告警草稿属于这个候选：材料已经装配好，模型整理后返回，应用检查并交给人阅读。服务端内部的计算再复杂，下一步业务行动仍由应用决定。

“受控模型调用”描述的是流程中模型所处的位置，网络请求的次数可以多于一次。有限的网络重试或明确规定的格式修正，都还属于这一方式。

### 预定义工作流：预先定义允许的状态与转移

如果任务包含多个阶段，而且阶段关系、路由规则和等待条件可以预先表达，就可以使用工作流。比如收集材料、生成报告、等待人工确认，再提交到事故记录系统。

有向无环图（DAG）只是工作流的一种表达方式。DAG 适合表达没有环的依赖关系；工作流也可以通过状态机表达循环、重试、等待和恢复。工作流是否持久化，取决于具体实现与存储机制。

工作流可以包含模型分类器。模型负责在几个类别之间选择时，外层允许的分支和转移规则仍由代码预定义，系统同样要说明这些边界。

### 受约束的智能体：在允许范围内动态选择下一步

当任务需要根据新证据反复决定查询什么、检查什么，以及是否继续调查时，可以评估智能体方案。

例如，只有看到日志中的某类异常后，才知道应进一步比较实例版本还是查询下游依赖。模型可以提出下一项调查动作，系统仍需要限制可用工具、参数范围、预算和终止条件。

路径不易预先确定，是引入智能体的必要理由之一，但还不充分。环境还要能提供可靠反馈，错误行动也要能被约束；两者缺一，把路径选择交给模型只会增加失败方式。

### 用比较表记录选择依据

| 当前主要问题 | 首先评估的方案 | 需要验证的条件 |
| --- | --- | --- |
| 规则与数据结构明确 | 规则程序 | 规则是否覆盖真实输入，异常能否被清楚处理？ |
| 需要整理给定的非结构化材料 | 受控模型调用 | 材料是否充分，输出能否被验证？ |
| 多步骤但阶段关系可定义 | 工作流 | 分支、等待、恢复和状态归属是否明确？ |
| 后续行动依赖新证据，需要动态调查 | 受约束的智能体 | 工具反馈、进展判断、终止与接管是否成立？ |

这份比较表用于组织设计讨论，没有经过统计验证。一个系统可以在不同环节采用不同方案。

## 2.4 标准一页方案：把判断写成可检查的清单

**要解决的问题**：怎样把前面的判断写成一份别人可以逐项追问的方案？

标准一页方案是全书共用的设计产物，共十二项，分为四组。每一项写结论、依据与未决事项；标为“待验证”的项目必须附上对应的实验。它用于准备设计讨论，写完并不表示方案可以上线。

| 编号与项目 | 必须回答的问题 |
| --- | --- |
| **问题** | |
| 1 任务与交付物 | 谁在什么时点、拿到什么、用来做什么？ |
| 2 错误后果与边界 | 做错了会怎样，哪些边界不能越过？ |
| **方案** | |
| 3 无需模型的基线 | 规则、查询、搜索或模板能做到什么，剩下什么缺口？ |
| 4 模型职责 | 模型具体做哪一件事，不做哪些事？ |
| 5 控制方式 | 选哪种控制方式与模式，为什么不选其他方案？ |
| **边界** | |
| 6 信息获取 | 材料来自给定输入、业务接口、检索还是记忆，权限与时效如何？ |
| 7 数据处理 | 哪些数据敏感，在哪里处理，是否传给第三方，保留多久？ |
| 8 动作与授权 | 会改变什么状态，由谁授权，是否需要审批？ |
| 9 状态与失败 | 保存什么，失败、超时、取消和结果不明时用户看到什么？ |
| **验证** | |
| 10 评测验收 | 用哪些样例、按什么标准判定，哪些由人工负责？ |
| 11 成本与延迟 | 按什么假设估算，怎样实测？ |
| 12 最小实验与改变条件 | 什么结果会推翻当前选择，什么需求变化会改变架构？ |

告警草稿第一版的填写如下：

| 编号与项目 | 告警草稿的第一版选择 |
| --- | --- |
| 1 任务与交付物 | 值班人员在告警出现后拿到有证据引用的待审阅草稿 |
| 2 错误后果与边界 | 关键数值错误使报告不通过；越权展示另行阻断；系统不关闭告警 |
| 3 无需模型的基线 | 固定模板已能集中展示材料，先与它比较 |
| 4 模型职责 | 整理现象、调查假设与信息缺口；不下根因结论 |
| 5 控制方式 | 固定流程中的受控模型调用（附录 F 模式 1），暂不自主查询 |
| 6 信息获取 | 调用方提供证据；没有知识缺口的证据前不加检索 |
| 7 数据处理 | 教学材料先脱敏；真实接入前核对处理位置、留存与用途 |
| 8 动作与授权 | 只生成草稿；数据权限由接入层保证 |
| 9 状态与失败 | 返回明确的失败状态，半份报告不算完成 |
| 10 评测验收 | 程序检查结构与引用，人工判断事实和调查价值 |
| 11 成本与延迟 | 记录输入输出规模、一次生成、人工审阅与失败调用 |
| 12 最小实验与改变条件 | 若主要缺口是取证，再评估固定查询与动态调查 |

空白表格见[附录 E 标准一页方案模板](../appendix/templates/one-page-design.md)，按十二项写完一个陌生需求的完整示范见[第一篇小结](reference-architecture.md)。场景篇和章末练习都采用这套编号。

## 2.5 在架构图上标明数据与动作边界

**要解决的问题**：架构图上除了“用户—模型—工具”，还必须画出什么？

只画“用户—模型—工具”三个方框，无法说明系统如何承担责任。至少还应明确：数据来自哪里，谁有权读取，哪些状态由应用维护，以及什么条件下允许改变外部世界。

对第一版告警助手，可以形成下面的职责表：

| 对象或行为 | 本阶段的责任归属 | 边界说明 |
| --- | --- | --- |
| 告警与证据包 | 调用方提供，应用校验 | 模型不能凭空补齐缺失材料 |
| 材料访问权限 | 接入系统与应用身份层 | 能引用一个 ID，还需另有读取授权 |
| 事实整理与调查假设 | 模型生成候选内容 | 应用校验结构，内容仍需评审 |
| 报告状态 | 应用设置 | 只有应用能把故障标记为已解决 |
| 操作执行 | 第一版不提供 | 后续接入时单独设计授权、恢复与审计 |

这张表是设计目标。第 5 章的本地示例使用人工提供的教学文件，只实现其中的输入与报告处理，并没有实现真实身份系统或生产数据接入。

### 数据去向必须成为方案的一部分

将输入、检索结果、模型请求、运行日志和人工审阅材料画成数据流，分别说明处理位置、第三方接收者、保留期限和删除责任。某个服务可以调用，只说明技术上可达；哪些业务数据可以传入，要单独决定。处理条件尚未确认时，可以先用合成或经核验的脱敏数据验证流程；真实数据准入仍是独立的决策。

信息不足时应选择补问、拒答或交给有责任的人处理，模型自报的高置信度代替不了证据（第 3 章 3.2 节）。涉及招聘、授信等对个人权益有重要影响的任务，还要单独设计复核、申诉及错误分布检查；具体法律适用见[附录 D](../appendix/compliance-cn.md)。评测所需数据也应有明确用途和访问边界，不为分析方便额外收集无关敏感信息。

### 只读操作同样有风险

读取日志不修改业务资源，但仍可能涉及敏感内容、跨租户数据或昂贵查询。因此，读写划分适合判断副作用，却不足以涵盖全部风险。

设计时还需要考虑数据敏感程度、可访问范围、调用资源消耗，以及结果会被谁看到。对读操作实施范围限制，与对写操作实施审批，是两个可以同时存在的控制措施。

### 将假设与事实分开存放

“模型怀疑发布有问题”是调查假设，“发布平台记录 09:58 完成版本更新”是带来源的材料，“系统已经回滚到上一版本”则需要执行结果支持。三者要在数据上保留类型区分，否则后续组件会把推测当作事实继续使用。证据地位的完整讨论见第 3 章 3.2 节，任务状态的设计见第 3 章 3.4 节。

## 2.6 在引入自主行动前验证反馈与退出机制

**要解决的问题**：允许模型选择下一步之前，系统要先具备什么？

智能体需要根据行动结果调整后续步骤。若工具只返回一段含糊的“处理成功”，模型与应用都难以判断任务是否有进展。

在告警调查中，查询结果可以提供时间范围、命中记录、统计口径与数据缺失情况。这些信息有助于判断一次查询是否新增了证据。相反，一段缺少来源的总结，可能让调查循环围绕相同猜测反复运行。

### 定义成功、失败与无法判断

对于报告生成，成功可以定义为产生符合约定的草稿。对于故障处置，成功需要根据业务状态核验，不能沿用“模型已经给出答案”的标准。

指标改善能支持的结论范围有限，第 1 章 1.7 节第三步已经用错误率回落的例子说明过：关闭事故需要另外的业务规则。

退出条件除了“成功”，还要覆盖其他结束方式。材料不足、权限不足、预算耗尽、外部服务不可用和人工取消，都可能是合理的结束路径。每一种路径都应保留当前材料并告知接手者，任务在这些路径上结束，而不是让模型继续尝试直到编出一个答案。

### 为结果不明的操作预留位置

后续如果允许创建工单或执行运维动作，请求超时后，动作可能已经完成，只是响应没有到达。安全重试依赖接口的幂等约定、操作标识和结果核对，第 3 章 3.6 节给出完整分析。架构选择阶段只需确定这些问题由谁负责；团队尚不能判断重复操作的后果时，可以先停留在只生成建议、由既有流程执行的范围内。

## 2.7 估算资源预算，说明假设与测量边界

**要解决的问题**：成本与延迟还没有实测数据时，怎样写进方案？

初步设计时不一定知道精确成本，但应当能解释成本由什么构成。按所选服务的实际计费项估算模型输入、输出、缓存或其他收费项目，再加入检索、工具、存储与运行开销；人工审阅与运维成本单独列出，避免混成一个看似精确的 API 价格。

```text
单任务资源费用 ≈ 各次模型调用费用之和 + 检索和工具费用 + 可归属的运行费用
成功任务平均资源费用 = 本批任务的总资源费用 / 本批经判定成功的任务数
```

第二个式子的分子包含失败任务的消耗；成功数为零时，该平均值无定义。是否计入人工费用，应在统计口径中注明。实际项目要按所选服务的价格与计量规则展开各项，Token 只是计费项之一。

延迟需要画出执行依赖。串行环节可以按同一场景估算耗时相加；可并行的阶段应看关键路径，并计入排队、调度与汇合开销。各服务的 P95 相加得不到端到端 P95，尾部延迟应对完整链路测量。

以下只是教学算例：假定一次请求有两个各 2 秒的模型调用，以及一次 0.5 秒的数据查询，不含排队。全部串行约 4.5 秒；如果两个模型调用没有数据依赖，并在查询完成后并行，理想情况下约 2.5 秒。实际结果还需测量并行资源争用与调度开销，这些数值仅用于演示计算方法。

方案应分别给出常规路径、允许的重试路径和预算耗尽时的行为。动态智能体的任务成本，要在步数、每步资源和总时限都有约束后才能估算。前期使用区间与明确假设，原型完成后用样例替换假设；未知费用标为“待测”，而不是写成零。

## 2.8 识别不值得引入模型的职责

**要解决的问题**：哪些职责应当留给确定性系统？

判断应针对具体职责。同一产品可以将理解交给模型，将计算和执行留在确定性系统。

| 需求或职责 | 优先候选 | 不直接交给模型的原因 |
| --- | --- | --- |
| 按明确公式计算金额、税额或库存 | 已验证的计算与业务规则 | 精确计算和审计需要确定的结果 |
| 根据角色判定能否访问订单 | 权限策略与资源归属校验 | 授权依据是身份与策略，与用户解释是否充分无关 |
| 固定字段映射、告警阈值、定时导出 | 普通代码或工作流 | 额外生成没有可证明的增量价值 |
| 查询当前订单状态或账户余额 | 权威业务接口 | 模型参数中的知识不是实时账本 |
| 材料缺失且没有合法获取渠道的诊断 | 补齐数据或人工调查 | 调用次数补不出业务事实 |
| 目标、错误后果与验收都未明确的自动执行 | 先澄清需求并建立受控试验 | 无法判断哪些行为可接受 |

这些职责中，模型仍然可以承担局部工作：

- 计算类：把自然语言转换成待校验的查询或参数。
- 授权类：帮助用户理解拒绝原因，授权结果保持不变。
- 固定映射类：输入确实含有难以规则化的文本整理需求时。
- 实时查询类：理解用户问题后调用接口，再解释结果。
- 缺材料的诊断：生成待调查清单，并标明无法确认的结论。
- 未定义的自动执行：定义边界、反馈与退出条件后再评估。

不选模型是针对当前条件的结论。输入结构、人工成本或能力需求变化时，应重新评估备选方案，并把变化的依据写进决策记录。

## 2.9 用架构决策记录保留推理依据

**要解决的问题**：怎样让后来者知道当初为什么这样设计？

架构图告诉后来者系统由哪些部分组成，决策记录解释为什么这样组合。后者在 AI 应用中特别有用，因为模型、提示、输入分布和业务要求都可能发生变化。

架构决策记录（Architecture Decision Record，ADR）通常包含背景、决策、状态与后果。Michael Nygard 的原始文章说明了这种轻量记录方式；本书在此基础上补充验证计划与重新评估条件，方便跟踪尚未确认的假设。[Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

下面是一份针对本书案例的设计记录示例。状态为“拟采用”，表示尚未取得线上效果。

### ADR-001：先构建只读告警草稿应用

**状态**：拟采用，完成应用边界验证与真实模型评测后再决定是否试用。

**背景**：教学场景中，输入包含告警、指标、发布记录与日志摘要。当前目标是辅助人工整理证据；自动处置的权限、反馈和恢复机制尚未建立。

**备选方案**：固定模板展示材料；固定流程调用模型整理草稿；由智能体主动查询并调查。

**决策**：保留固定模板作为比较基线，先实现“输入校验—模型整理—结果校验—人工审阅”的流程。第一版不提供生产写操作，也不让模型自行扩展查询范围。

**理由**：当前任务的输入和交付物能够明确描述，尚无证据表明动态选择工具能够带来足够的增量价值。先缩小范围，有利于定位事实错误和材料缺口。

**代价**：应用无法主动补齐证据；分析质量依赖输入材料；真实模型生成仍需要语义评测与人工审阅。固定流程也不能保证每份报告内容正确。

**验证计划**：先用本地保存响应检查输入、引用和失败处理，再用真实模型测试正常、缺失、冲突和误导性材料。对照固定模板评价任务通过情况、人工修订与耗时。

**重新评估条件**：如果试用表明主要瓶颈是材料缺失，先评估增加固定查询步骤；若查询路径确实依赖中间证据，再设计受约束的动态调查。是否增加自主性由对照结果决定。

**尚未确定事项**：在线模型、具体服务预算、数据接入权限和上线阈值。未确定之前，不把方案标记为可上线。

这份记录没有复杂的评分，但每个关键取舍都可以被追问。条件变化时，团队更新状态或新增替代决策，原来的背景保留在记录中。

## 2.10 把架构结论变成下一步实验

**要解决的问题**：架构讨论结束时，团队手里应该有什么？

架构讨论的结束点是一份可以实施的验证计划，“我们决定使用某框架”还算不上结束。

对本书案例，下一步可以分为三项交付：定义证据包与报告契约，实现最小处理流程，以及准备能区分有效整理和错误推断的样例。第 4、5 章建立最小实现，第 6 章系统说明评测集与判对错方法。

在进入实现前，可以用四个问题检查设计是否足够清楚：

1. 如果暂时不用模型，业务还有哪种可行做法？
2. 模型失败或无法判断时，用户会得到什么？
3. 哪些性质能由代码验证，哪些只能通过内容评审与实验评价？
4. 哪个结果会让我们放弃当前方案，或者推迟增加复杂度？

如果第四个问题没有答案，方案可能还只是技术愿望。一个可以被证据推翻的设计假设，才有机会通过实验得到改进。

## 本章小结

1. 架构推导从业务任务开始：先拆出交付物、使用者与使用时点，再区分事实、假设与约束。
2. 成功标准写在方案之前，指标要写明对象与分母，并保留一个无需模型的基线。
3. 四种控制方式按“下一步由谁决定”区分，可以在同一系统的不同环节组合使用。
4. 标准一页方案按问题、方案、边界、验证四组共十二项书写，是全书共用的设计产物。
5. 数据去向、动作授权、反馈与退出、资源预算都要在方案中写明责任归属。
6. 架构决策记录保留背景、理由、代价与重新评估条件，让方案能够随证据更新。

第 3 章转向实现前最容易混淆的几组概念：证据、记忆、任务状态、校验与恢复。

## 迁移练习

实验室希望研究人员说一句话就能借用仪器、查使用规程并预约时段。请用标准一页方案的十二项写出第一版。

### 参考思路

本题给出一份完整填写的一页方案，供对照检查。

**问题**

- **1 任务与交付物**：研究人员提出使用需求时，拿到适用规程的回答、可用时段，以及经确认后的预约结果。
- **2 错误后果与边界**：规程解释错误可能导致违规操作；预约冲突浪费机时；系统不得替无资格人员预约，也不得绕过培训要求。

**方案**

- **3 无需模型的基线**：仪器目录与规程搜索、现有预约表单；先测量研究人员用表单完成预约的耗时与出错点。
- **4 模型职责**：把自然语言请求解析为仪器、时间范围与用途字段；基于检索到的规程解释注意事项。资格判定与冲突检查不由模型承担。
- **5 控制方式**：入口按“问规程”“约时段”分流；预约走预定义工作流：解析 → 校验 → 查询时段 → 用户确认 → 提交。规程问答用检索增强生成（附录 F 模式 8）；步骤固定，不采用自主规划。

**边界**

- **6 信息获取**：规程来自实验室审定的文档，按仪器型号与版本检索；可用时段和使用资格来自预约系统与培训记录的权威接口。
- **7 数据处理**：研究人员身份与项目信息属于内部数据；发往外部模型服务前确认处理位置与留存，课题敏感信息不进入提示。
- **8 动作与授权**：查询为只读；提交预约是写操作，以研究人员本人身份执行，由预约系统检查资格与冲突；需要导师批准的仪器沿用现有审批。
- **9 状态与失败**：保存解析结果、确认状态与操作标识；时段已被占用时请用户重选；提交超时按操作标识查询，确认前不重复提交。

**验证**

- **10 评测验收**：样例覆盖：表述完整、缺少时间、仪器名称有歧义、无培训资格、规程无相关条款。字段解析由程序比对，规程回答由仪器管理员判定。
- **11 成本与延迟**：每次请求一次解析调用；问答一次检索与一次生成；以“说出需求到看到可选时段”为起止点测量。
- **12 最小实验与改变条件**：若表单在耗时与出错率上不差于自然语言入口，保留表单；需求变为故障诊断且下一步检测依赖反馈时，再评估只读范围内的受约束智能体。

**需要追问**：是否已有结构化目录和预约接口？谁有仪器使用资格，培训记录由谁维护？哪些仪器需要人工批准？

**暂不采用的方案**：实时可用时段不放进文档问答；阶段明确，不采用自由规划；仪器目录很小时，表单可能已经足够。

**改变选择的条件**：新增审批只需在工作流中增加审批步骤，控制方式不变；只有动态诊断才需要重新评估第 5 项。

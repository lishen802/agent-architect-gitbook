# 第 6 章 评测基础：建立任务集与判断结果

> **已有经验**：测试用例、验收标准与对照实验。
>
> **新增问题**：开放式输出允许多种答案，评分器也需校验。
>
> **本章产出**：一份任务集、逐项判定记录、可复核汇总与改进实验。

第 5 章已经验证：输入不合法时不调用模型，报告引用不存在的证据时不返回草稿。但即使程序完全遵守这些规则，模型仍可能把“发布后发生异常”写成“发布导致异常”。接口测试没有失败，用户却得到了错误判断。

本章要补上内容与任务层面的验证。我们仍然保留代码测试，把生成结果能否满足需求作为另一组检查。目标是让开发者能够独立建立第一份任务集，并解释为什么一份输出应该通过或不通过。

## 6.1 先确定评价单位

评价单位可以是一个抽取字段、一条答案或一次完整任务。选择不同单位，得到的通过率含义也不同。

对告警助手，一次任务从接收符合约定的材料开始，到返回可供审阅的草稿或明确的异常结果结束。我们需要记录调用是否完整、结构是否有效、事实是否受支持、是否遗漏重要缺口。任务结果不能仅由“返回了 JSON”判定。

如果评价工具执行，结果还包括外部状态。例如，创建工单是否成功，要核对工单记录，而不只是检查模型回复中有没有“创建成功”。过程检查用于判断是否越权、是否违反必要约束；在没有业务要求时，不强制所有正确解法使用同一条工具路径。

## 6.2 一条样例应该包含什么

只收集问题和一段参考答案，往往不足以评价系统。应当同时保留任务成立的条件与判断依据。

| 字段 | 用途 | 告警示例 |
| --- | --- | --- |
| 任务 ID 与类别 | 追踪同一问题与覆盖范围 | 发布时间相关性 |
| 需求与输入版本 | 明确本次允许使用什么 | 固定指标、发布与日志材料 |
| 前置环境与权限 | 限定可执行范围 | 只读，没有回滚能力 |
| 必须满足的检查项 | 定义可观察结果 | 保留数值、区分观察和假设 |
| 禁止结果 | 明确严重错误 | 无依据确认根因或宣布恢复 |
| 允许的变体 | 避免误拒合理答案 | 可以用不同措辞指出因果未确认 |
| 判定方法与证据 | 说明由谁判、凭什么判 | 引用程序检查，语义人工评审 |
| 来源与维护记录 | 判断样例有效性 | 教学构造或已脱敏事件，记录修订 |

模板见[评测样例模板](../templates/evaluation-case.md)。环境信息只保留必要内容，不能把生产凭证放进评测文件。

下面是一条人为构造的样例摘要，不是已经测出的效果：

```text
任务：根据 E1 错误率与 E2 发布记录整理告警草稿。
E1：10:00—10:10 的 HTTP 5xx 比例为 5.2%。
E2：09:58 完成发布。
必须：保留错误比例；把发布相关性作为待调查方向。
禁止：宣称全部请求失败；宣称已确认发布导致异常。
允许：指出缺少版本对照数据；只列出可靠观察并提出缺口。
人工判定：逐项核对发现与材料，不按措辞完全相同评分。
```

把参考答案写成唯一文本，会惩罚同样正确的表达。更稳妥的做法是先写检查项，再给一份示例答案帮助评审者理解尺度。

## 6.3 从需求边界组织任务集

任务集不能只包含最容易演示的成功路径。可以先围绕会改变处理方式的条件选样例：

| 条件 | 样例设计 | 检查重点 |
| --- | --- | --- |
| 材料充分 | 证据完整且相互一致 | 能否提供有用结果，而非一律拒答 |
| 信息缺失 | 缺少关键时间或业务数据 | 是否说明缺口而不补造事实 |
| 材料冲突 | 同口径记录给出不同值 | 是否识别冲突，保留核对入口 |
| 时间与范围不符 | 旧文档、其他服务或其他租户 | 是否错误套用材料或泄露内容 |
| 指令污染 | 文档正文要求忽略任务 | 是否改变原任务或执行未授权动作 |
| 依赖异常 | 超时、拒绝、部分输出 | 是否保留正确失败状态 |

没有适合所有业务的固定样例数。早期先覆盖明确的行为边界，再根据试用失败和输入分布补充。若样例很少，保留逐条结果比宣称一个高精度百分比更有意义。

同一次事故的改写、同一文档的近似问题，不宜被误当作许多独立事件。开发样例可以帮助修改提示；保留样例用来阶段性检查迁移效果。频繁根据保留样例调参后，就应承认它们已经参与开发，并补充新的评价材料。

## 6.4 按检查项选择判定方法

程序检查、模型辅助评分与人工评审可以组合使用，各自承担不同职责。这种划分可参考 [Anthropic 的评测工程说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。以下安排是针对本书案例的设计，不是统一评分标准。

**适合程序检查的项**包括结构、字段范围、引用是否存在、权限边界、外部状态和预算消耗。程序检查的结论受规则覆盖范围限制；通过引用 ID 检查不能证明该引用支持文字含义。

**适合人工判断的项**包括材料是否支持结论、回答是否遗漏关键条件、澄清问题是否必要。评审者应使用相同说明；遇到分歧先检查任务是否含糊、材料是否充分，再讨论评分。不能默认任何一位评审者天然无误。

**模型辅助评分**可以帮助筛查大量开放式结果，但它也需要验证。先用人工已判定的样例检查误判与漏判，给评分器提供判断依据，允许它报告无法判断。不要让回答模型仅凭自己生成的理由为自己盖章；也不要把评分模型的一个数字当作客观真值。

评测器也可能有错误。可用一个已知合格结果和一个带明确错误的结果检查它是否区分正确。例如，两个输出只在“发布可能相关”和“已确认发布导致异常”上不同，判定过程应能解释差别。

## 6.5 避免指标掩盖失败

为每次试验保留原始判定与原因，再决定如何汇总。可分别报告完整生成比例、契约通过比例和任务通过比例，明确各自的分母。

对“应当回答”和“应当拒绝或澄清”的样例分别统计。一个系统如果对所有问题都回答“不知道”，可能减少部分错误陈述，却没有满足可回答任务的目标。反过来，强行给答案也不能算完成缺失材料任务。

严重错误应单列，例如未经授权读取数据或重复提交高风险动作，不用平均表达质量将它们抵消。具体上线阻断规则由业务风险与验证计划确定，本章不提供未经实测的通用阈值。

对同一任务进行多次试验时，应保留每次结果、模型和提示版本，以及运行条件。只展示最后一次成功会掩盖不稳定性。不同试验共享缓存、环境残留或外部服务故障时，不能未经检查就假定完全独立。

## 6.6 对照实验怎样帮助选架构

继续使用告警助手，可以比较固定模板与模型草稿。两种方案接收相同材料，用相同任务标准判断；分别记录整理效果、关键错误和人工修订成本。

若增加检索，还应检查是否因为补充了正确材料而改善，而不是同时更换模型、提示与任务集后把全部收益归功于检索。无法分离变量时，可以评价组合方案，但要限制归因。

一个适合早期项目的比较过程是：固定输入与标准，保存每个方案结果，尽量隐藏方案名称并交换展示顺序进行评审，记录分歧与失败，再决定保留、修改或放弃。以上是实验设计建议，不是本书已经开展的用户实验。

对执行型系统，固定测试环境或保存可重建的外部状态同样重要。否则第二个方案可能面对第一个方案已经修改过的资源，比较失去意义。涉及实际副作用时应在隔离测试环境验证，不将模拟结果冒充生产保证。

## 6.7 让评测结论决定下一步

评测的产物应当能改变设计。如果问题来自缺失材料，先改信息获取；如果来自判断标准含糊，先改需求；如果来自重复执行，检查状态与接口契约。不是所有失败都应通过增加提示或模型角色来解决。

记录表至少包含任务 ID、输入版本、方案版本、调用是否完成、逐项判定、失败原因与评审信息。真实服务提供的耗时和用量可以另列，缺失数据标记为未知。

第 5 章的本地回放只验证应用处理链路；下文用人工构造材料完整演示评测流程，本章没有新增真实模型准确率或成本结论。发布回归、灰度、线上追踪与失败回流在第 20 章继续讨论。本章回答的是：如何建立一份足以开始比较方案的任务集，以及怎样判断结果。

## 6.8 完整示范：先写验收规则，再看候选答案

前面说明了方法，现在把它用于一次告警草稿评测。所有输入、候选输出和参考判定均为本书构造的教学材料，没有调用真实模型，也没有邀请外部评审者。配套程序实际执行的是记录检查与结果汇总，不能把汇总数字当作某个模型的能力指标。

### 第一步：固定本次要评价的需求

值班人员需要一份 payment-api 的告警草稿。草稿应保留材料中的关键数字与适用范围，区分观察和待验证解释，指出继续调查需要补充什么；本阶段不执行操作，也不要求确认根因。

在这次教学评测中，材料足以整理观察时应返回草稿；缺少目标服务数据、关键窗口，或存在未解决的同口径冲突时，返回信息不足并说明缺口。超时虽然可以被应用安全处理，但没有交付所要求的草稿，因此记为任务未通过。这里的状态约定来自本次需求，并非所有产品必须采用的统一规则。

同时固定判定表，避免看完答案再临时调整“什么算对”：

| 检查项 | 通过条件 | 失败例子 | 判定方式 |
| --- | --- | --- | --- |
| 报告契约 | 字段与类别符合本地约定，引用 ID 存在 | 引用 E999，但材料没有 E999 | 程序检查 |
| 数值与事件转述 `facts` | 报告中的数值、事件及其归属有材料依据 | 将别的服务的比例写给当前服务 | 逐项对照材料 |
| 适用范围 `scope` | 不扩大服务、环境、时间或人群范围 | 样本日志被写成所有请求的事实 | 语义判定 |
| 不确定性 `uncertainty` | 不把相关写成因果；保留缺失与冲突 | 仅凭发布时间确认根因 | 语义判定 |
| 任务帮助 `usefulness` | 有材料时整理有效观察，有缺口时提出相关问题 | 一律拒答，或绕过冲突直接建议处置 | 语义判定 |

在本示范中，契约、输出状态和四项语义检查都满足才算通过。已发现阻断性错误就记为失败；尚无已知错误但评审未完成时记为待定，不计入通过。若一个错误同时触及多项标准，可以保留多个标签，但汇总任务数时只算一个失败任务。

注意，`facts` 特意聚焦数值与事件的转述，因果判断交给 `uncertainty`。真实项目也可以采用其他划分，但必须先说明口径，避免两位评审者用同一个名称表达不同标准。

### 第二步：围绕会改变处理方式的条件选题

配套[任务集](../examples/evaluation-basics/cases.json)保存完整材料、输入版本、预期状态、必须满足项与允许变体。每题都有一条对应的[候选输出与参考判定](../examples/evaluation-basics/runs.json)。

| 任务 | 输入中的关键条件 | 应怎样处理 | 构造的候选结果 |
| --- | --- | --- | --- |
| T01 时间相关性 | 错误比例上升，发布先于指标窗口，没有版本对照 | 整理观察，因果保持未确认 | 数字正确，却宣称已确认发布导致异常 |
| T02 材料缺失 | 只有“错误增加”告警，没有比例与窗口 | 明确缺口，要求补材料 | 正确返回信息不足并列出所需材料 |
| T03 同口径冲突 | 两份记录对相同窗口分别给出 5.2% 与 0.2% | 保留冲突，先核对来源 | 只引用 5.2%，跳到是否回滚 |
| T04 范围不符 | 目标是 payment-api，只有已授权的 inventory-api 旁证 | 说明目标服务材料缺失 | 把旁证数值套给目标服务 |
| T05 应当回答 | 与 T01 相同的指标和发布材料 | 整理现有观察，提出针对性的后续问题 | 正确保留观察与因果边界 |
| T06 调用超时 | 输入足以形成草稿，但调用超时 | 记录调用失败，不删掉这次任务 | 无候选报告 |

T01、T05 和 T06 使用相同材料，刻意展示不同结果与失败层次，因此不能当成三个独立事故样本。六题的作用是演示判定流程，不代表业务流量分布，也不足以估计生产成功率。

T04 的旁证已经获得读取授权。本题只测试证据适用范围，不测试跨租户授权。若要评估权限，应另建身份、资源与工具轨迹可控的样例；仅检查一段文本无法证明系统没有越权读取。

## 6.9 逐条判定：合法结构为什么仍会失败

先看 T01 的两条证据：

```text
E1：payment-api 在 10:00—10:10 的 HTTP 5xx 比例为 5.2%，
    此前十分钟为 0.2%。
E2：payment-api 在 09:58 完成 v1.8.3 发布。
    未提供不同版本实例的对照数据。
```

构造的候选报告包含以下片段：

```json
{
  "kind": "hypothesis",
  "text": "已确认 v1.8.3 发布导致错误率上升。",
  "evidence_ids": ["E1", "E2"]
}
```

程序可以确认类别合法、文字非空、引用存在；它不能因此证明文字受证据支持。`hypothesis` 标签也不能抵消句子中的“已确认”。

按预先定义的标准，数值与事件转述通过，范围通过，不确定性失败。报告虽提供了一些有用材料，任务仍失败。判定理由应指向具体输出和输入缺口：“E1、E2 只有时间先后与指标变化，缺少足以确认因果的证据”，而不是只写“回答不好”。

一种可接受的改写是：“发布早于指标窗口，可以作为待调查方向；目前不能确认因果，需补充不同版本实例的指标。”也可以不提出发布假设，只保留两项观察并指出需要对照。两种表达都可能满足本题，不应为了匹配单一参考答案而拒绝其中一种。

### T02 与 T05：正确承认缺口，不等于总是拒答

T02 的材料缺少比例和窗口，参考输出指出这两个缺口并请求补充，因而通过。T05 已经有可用指标和发布时间；如果它也只回答“资料不足，无法分析”，就没有完成整理已有观察的职责。

本次 T05 的构造输出保留指标、说明发布先后但不确认因果，并提出版本对照问题，因此通过。评审时应同时保留这两类题，防止把“减少错误陈述”错误地优化为“什么都不做”。

### T03 与 T04：引用存在仍可能用错材料

T03 的 5.2% 确实来自 E1，所以局部数值转述没有错误。失败发生在忽略同口径冲突：报告没有告诉用户 E2 给出了另一个值，也没有提出核对来源。增加引用 ID 检查不能解决这一问题。

T04 则把 inventory-api 的数值写成 payment-api 的事实，同时违反归属和范围要求。修正方向是保留服务标识、限制材料适用范围，缺少目标数据时明确说明，而不是补充更多泛化说明。

### T06：安全处理失败与完成业务任务分开记录

T06 没有报告，无法做报告契约和语义评分。这不意味着可以从任务集删除它。本次需求需要一份合格草稿，所以任务记为失败；程序是否正确捕获超时，则由应用边界测试另行判断。

同一个试验可以同时得到“错误处理符合设计”和“业务任务未完成”两个结论。它们评价不同对象，并不矛盾。

## 6.10 运行汇总，并检查分母

配套目录提供一个只依赖 Python 标准库的[评测记录示例](../examples/evaluation-basics/README.md)。它不调用模型，不自动判断自然语言是否正确，也不代替第 5 章的 Go 校验器。它读取已构造的语义判定，执行一组明确标注范围的报告检查，再按规则汇总。

从仓库根目录执行：

```sh
python3 -B -m unittest discover -s examples/evaluation-basics -v
python3 -B examples/evaluation-basics/summarize.py
```

本轮运行已得到以下计数，完整输出保存在[summary.json](../examples/evaluation-basics/summary.json)：

| 项目 | 数量 | 口径 |
| --- | --- | --- |
| 计划任务 | 6 | 每题恰好一条试验记录，包含超时 |
| 完成生成 | 5 | T06 超时，无报告 |
| 报告契约通过 | 5 | 五份已返回报告都通过本地契约检查 |
| 任务通过 | 2 | T02、T05 |
| 任务失败 | 4 | T01、T03、T04、T06 |
| 任务待定 | 0 | 当前参考判定齐全 |

如果只汇报“返回报告的契约通过数为 5/5”，就看不出其中三份报告存在任务层面的错误，也看不出另一次调用没有返回。采用全计划任务口径时，任务通过数是 2/6。两项数字都可以报告，但必须带上对象与分母，不能把前者简称为“系统准确率”。

这些数字只描述人为构造的记录。它们没有模型身份、实际生成用量或线上耗时，因而不能用于模型选型、效果排名或成本估算。示例用 Python 是为了让读者直接查看记录与计算规则，不改变本书主要业务实现采用 Go 的安排。

### 汇总程序也要防止产生好看的错误结果

示例拒绝缺记录、重复记录和未计划的任务 ID，避免分母静默变化。如果完成生成的样例没有语义判定，则记为待定；缺少某个应填判定字段则报记录错误，不能默认通过。

本轮五项测试验证了这些关键行为，也验证了不存在的引用会阻断任务，即使语义判定全被填写为通过。测试通过只说明这些汇总与检查规则在所测条件下工作，不说明参考语义判定经过独立专家确认。

这个小程序只支持每题一次试验。真实模型需要重复试验时，应显式增加试验编号与计划次数，分别保留任务数、尝试数和每次结果；不能复制成功记录来提高计数，也不能把多次尝试误写成更多独立任务。

## 6.11 从失败记录推回设计选择

完成评分以后，不应立即得出“需要更强模型”或“需要智能体”的结论。先问失败发生在哪个环节，再选择能够检验该解释的改动。

| 观察到的问题 | 候选解释 | 下一项实验 | 当前不值得直接增加的复杂度 |
| --- | --- | --- | --- |
| T01 因果越界 | 指令、示例或判定约束没有充分约束因果表述 | 固定材料与模型，改变说明或示例，复查因果题和正常回答题 | 没有证据表明需要多智能体投票 |
| T03 忽略冲突 | 材料呈现没有凸显冲突，或生成阶段未处理冲突 | 明确呈现来源与相同口径；检查输出是否保留矛盾 | 单纯增加检索可能引入更多矛盾 |
| T04 范围错配 | 材料适用对象与当前目标没有被正确区分 | 将目标与证据元信息显式关联，并加入错配回归题 | 更长上下文不能自动纠正归属 |
| T06 超时 | 依赖、配置或预算问题，原因尚不确定 | 查看调用证据，定位失败阶段，再决定重试与截止策略 | 未定位前不扩大模型调用次数 |

这些是待检验的解释，不是从六条构造记录得出的真实系统根因。不能只修改一条样例使它通过，就声称架构优化有效。

### 与无需模型的基线比较什么

对 T01，可先用固定表格展示 E1 的比例和 E2 的发布时间，并统一提示“原因尚未确认”。这个基线没有生成新的因果结论，但它能保存现有观察。模型方案需要证明，它在遵守同样边界的前提下，提供了更有用的整理或后续问题。

可以让评审者对相同材料下的两份结果分别记录关键错误、遗漏和后续调查价值，再在实际试用中记录审阅与修订负担。本章没有运行这样的读者实验，也没有提供基线优于模型或模型节省多少时间的结论。固定模板的真实局限，也要在材料变化和异常路径下检查，不能因为它不生成文字就预先宣称完全可靠。

### 修复一条答案与验证一项改动的区别

把 T01 中“已确认”改成“可能相关”可以演示一种答案修正，却没有证明提示改动能稳定得到这种结果。下一轮应保留输入、评分标准和比较条件，重新取得整个开发任务集的输出，并记录原有通过项是否退化。

因为这些题已经参与设计和修改，它们属于开发及回归材料。阶段性验收还需要新的未参与调参任务，来源与已有题尽量避免同事件改写的重叠。当前六题没有保留测试集，也没有覆盖不同规模、语言、权限和真实工具状态，不能直接承担上线验收。

## 6.12 评审分歧与下一轮验证怎样处理

假设一位评审者认为“发布后错误上升”只是时间描述，另一位认为读者会将其理解为因果。这个分歧可能来自措辞，也可能来自标准不清。此处是假设情形，并非本书已经取得的试读反馈。

先保留各自判断和具体依据，再检查题目是否要求区分时间关系与归因。如果规则没有说清，应补充可接受与不可接受的表述边界，给规则增加版本，并按新口径重新检查受影响结果。不能只改不喜欢的分数而保留旧规则。

无法达成判断时，记录待定、缺失证据和处理责任人。若材料本身存在无法判定的错误，应修正或隔离该题，同时保留原因和原记录。删除难题后重新汇总，会改变评价范围，必须明确披露，不能把分母缩小伪装成质量提升。

规模扩大后可以引入模型辅助判定，但先检查它能否区分本章这些已说明理由的结果，尤其是引用存在却不支持结论、信息不足时合理拒答、材料足够时过度拒答。保留人工复核和无法判断的出口，不让评分模型只根据答案语气或自信程度下结论。

接入真实模型前，应准备输入版本、任务标准、实际模型标识、提示与应用版本、试验次数、输出原文、结束状态和判定记录。调用费用和延迟有实际记录再填写；缺失就标为未知。出现关键事实错误时是否阻断上线、哪些任务必须人工复核，要在实际业务风险下约定，本章不替不同项目设一个通用通过率。

到这里，读者应能交付四份相互对应的材料：任务集、候选结果、逐项判定、带限制与下一步实验的结论。评测的价值在于使下一项工程决策有据可查，而不是生成一个孤立的总分。

## 本章小结

评测把业务要求变成可检查的任务与结果。代码测试和任务评测相互补充；参考答案帮助说明尺度，不能替代对允许变体和失败条件的定义。只有保留适用范围与失败证据，评测才有助于架构决策。

报价整理助手要对比三家供应商的交付条件。请设计评测，不要求生成一篇固定措辞的答案。先按第 2 章的一页方案组织答案，再阅读参考思路。

### 参考思路

**当前选择**：固定原始报价与版本，分别检查价格单位、税费和交付条件；允许多种表达，缺失信息需标注。以人工整理表为比较基线。

**需要追问**：如何定义可比较报价，哪些条款必须由采购人员核对，实际结果如何计入失败与人工修订？

**暂不采用的方案**：不只比较文字相似度，不让模型自评分成为唯一验收；代码测试继续检查解析与业务规则。

**改变选择的条件**：如果新增自动下单，评测必须加入授权、外部状态和重复提交，不能沿用文本评分作为全部验收。

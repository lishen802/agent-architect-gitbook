# 第 5 章 构建第一个可验证的 AI 应用

上一章定义了模型调用的交互契约。本章将它放进一个完整但范围有限的应用：输入一份告警证据包，输出供值班人员审阅的分析草稿。

这个应用的目标，是减少值班人员整理材料的重复工作。它需要说明发生了什么、哪些方向值得调查，以及当前还不知道什么。至于是否回滚发布、重启实例或关闭告警，仍由后续调查与既有运维流程决定。

从一个小任务开始，可以让我们更容易看清系统的责任。即使没有工具调用、知识库和智能体循环，输入质量、输出约束、失败处理与效果验证也已经构成了一个完整的工程问题。

本章配套程序分为两个层面的使用方式：可以立即运行本地响应回放，验证应用逻辑；也可以按照本章最后的接入步骤实现真实模型适配器，进一步评价生成效果。仓库中已经实现前者，尚未包含在线供应商适配器或真实模型评测结果。

## 5.1 先定义这次任务的交付物

假设值班人员收到 `payment-api` 服务的错误率告警。已有系统提供了三条材料：

| 证据 ID | 来源 | 内容 |
| --- | --- | --- |
| E1 | 监控指标 | 10:00—10:10 的 HTTP 5xx 比例为 5.2%，此前十分钟为 0.2% |
| E2 | 发布记录 | 09:58 完成版本 v1.8.3 发布 |
| E3 | 日志摘要 | 抽样日志出现多条下游超时，尚无完整计数与下游监控 |

本章中的服务、时间和数值均为教学构造，不代表真实生产事故。

这些材料支持一些明确的观察：错误比例上升，发布时间早于告警窗口，抽样日志包含超时。它们也提示了可能的调查方向，但还不能证明新版本或某个下游服务就是根因。

因此，一份合格的交付物应当做到三件事：保留关键观察，标明调查假设，列出有助于继续调查的问题。例如，比较不同版本实例的错误率，或者检查下游服务在同一时段的表现。

### 把“成功”写得足够具体

如果需求只有“生成一份专业报告”，开发者很难判断何时可以交付。我们将验收要求拆为两组。

第一组是程序可以检查的条件：

- 输入具有告警标识、服务名称和有效时间窗口。
- 证据条目具有唯一 ID、来源、时间与正文。
- 报告遵守固定结构，发现必须引用本次输入中的证据。
- 信息不足时列出待确认事项。
- 调用失败或输出不合格时，不把原始文本当作合格报告返回。

第二组需要内容评审：

- 是否遗漏关键事实或改变了数值含义。
- 是否把时间先后误写成因果关系。
- 引用的证据是否真正支持相应发现。
- 是否无依据地扩大影响范围。
- 待确认事项是否能帮助值班人员继续调查。

这两组要求分别对应应用边界和任务质量。前者通过，不代表后者自然成立。

## 5.2 用证据包建立可追溯的输入

如果把告警、日志和发布信息拼成一大段文字，模型可能仍然能够理解，但系统很难追踪每项结论来自哪里。为材料分配稳定的引用标识，可以让回答与原始记录建立联系。

配套程序采用以下输入类型，代码节选如下：

```go
type Evidence struct {
    ID         string `json:"id"`
    Source     string `json:"source"`
    ObservedAt string `json:"observed_at"`
    Text       string `json:"text"`
}

type AlertInput struct {
    AlertID     string     `json:"alert_id"`
    Service     string     `json:"service"`
    WindowStart string     `json:"window_start"`
    WindowEnd   string     `json:"window_end"`
    Evidence    []Evidence `json:"evidence"`
}
```

`Evidence.ID` 只在本次证据包中用于关联引用。真实系统还应保留可以定位原始材料的记录标识，并在输入装配时检查访问权限。本地演示文件是显式提供的教学数据，示例没有实现身份认证或多租户权限系统。

时间也有两种含义：告警观察窗口描述当前分析范围，证据时间描述记录发生或采集的时点。发布记录可能早于告警窗口，因此不能把所有窗口外材料一概判为无效。

### 在调用前拒绝无法处理的输入

示例检查服务名与告警标识非空、时间可解析、窗口结束晚于开始、证据 ID 不重复，并设置条目与载荷上限。

这些限制不是行业通用阈值。示例使用最多 100 条证据、单条正文最多 8 KiB、输入文件最多 256 KiB，目的是防止教学程序无界读取与处理材料。字节上限也不是模型上下文的 Token 上限；真实接入还要执行对应模型的预算检查。

对于结构合法但证据为空的请求，应用直接返回 `needs_review`，原因是 `no_evidence`，不调用模型。重复请求不能产生不存在的监控数据，尽早返回能节省等待和调用资源。

这一判断并不是“没有三条证据就不能分析”。有一条有效材料时，模型仍可能帮助整理事实；是否足以形成有用的草稿，要结合材料内容判断。

## 5.3 组织最小处理流程

应用流程可以表示为下面的处理顺序。每一阶段都可能提前结束，而不是必须走到生成报告这一步。

```text
读取并校验证据包
        ↓
检查证据是否为空
        ↓
构造任务指令与输入数据
        ↓
在截止时间内调用模型
        ↓
检查生成是否完整
        ↓
解析对象并校验业务约束
        ↓
返回待审阅草稿或明确的异常状态
```

模型只负责中间的内容生成。是否接受输入、是否允许等待、是否接受输出，以及对用户返回哪一种状态，都由应用决定。

这样的流程还有一个好处：每一段责任都可以单独检验。当报告有问题时，团队能够区分是材料不足、生成失败、校验规则不够，还是内容评审发现了语义错误。

### 通过接口隔离内容生成

上一章的 `Model` 接口在这里成为应用与生成组件之间的连接点。业务函数 `Analyze` 接收输入与模型实现，返回统一的结果对象。

以下为流程节选，完整输入检查与错误分支见[配套源码](../examples/alert-assistant/main.go)：

```go
callCtx, cancel := context.WithTimeout(ctx, 10*time.Second)
defer cancel()

response, err := model.Generate(callCtx, Request{
    Instructions:  instructions,
    InputJSON:     input,
    PromptVersion: promptVersion,
})
```

同一个接口可以由真实服务适配器实现，也可以由测试替身实现。本章使用 `SavedResponse` 从本地文件读取提前保存的输出，它不会分析输入，也不会生成新内容。读者必须为输入选择对应的响应文件。

为什么先使用它？因为我们首先需要知道：空证据是否会阻止调用，未知引用是否会被拒绝，截断结果是否会被错误地返回给用户。这些性质不应依赖某次模型恰好生成了什么。

测试替身能够验证处理逻辑，却不能证明提示有效，也不能测量模型理解能力。切换到真实模型之后，仍需进行后文的效果评测。

## 5.4 检查结果的形状、引用与含义

应用接收生成结果后，先判断它是否完整，再解析内容。如果供应商表示输出被截断，即使剩余文本碰巧可以解析，也不能据此认定整个任务已经完成。

本地响应回放只有文本文件，没有供应商元数据，因此把成功读取的文件视为一次完整生成。截断与拒绝等情况在测试中通过专门的模型替身注入。真实适配器必须从响应协议中获取结束原因。

### 解析之后还有业务校验

报告结构如下：

```go
type Finding struct {
    Kind        string   `json:"kind"`
    Text        string   `json:"text"`
    EvidenceIDs []string `json:"evidence_ids"`
}

type Report struct {
    Assessment    string    `json:"assessment"`
    Findings      []Finding `json:"findings"`
    OpenQuestions []string  `json:"open_questions"`
}
```

仅仅将 JSON 反序列化到这些类型，还不足以确认字段齐全。Go 中缺失字段可能保留零值，因此示例继续检查报告类别、数组是否存在、文本是否为空，以及信息不足时是否解释了缺口。

解析器还会拒绝未知字段、多个连续 JSON 对象及非对象输入。这里使用 Go 标准库的 `encoding/json`，相关行为见[官方包文档](https://pkg.go.dev/encoding/json)。它仍保留标准库对于重复键、字段名匹配等的既有处理方式；示例没有实现完整 JSON Schema 校验器，也不宣称已经解决所有 JSON 解释差异。

应用额外限制报告最多 12 项发现与 12 个待确认问题，每项发现都必须引用已知且不重复的证据 ID。这些限制控制展示规模和引用关系，不判断文字的真实性。

### 一个有效引用也可能支持错误结论

假设报告写道：

> 已确认新版本导致全部支付失败。证据：E1、E2。

E1 和 E2 都存在，所以引用完整性检查可以通过。但“全部支付失败”与 5.2% 的 HTTP 5xx 比例不是一回事，“发布时间相近”也不能确认因果关系。

这正是工程校验的边界。示例无法凭引用 ID 自动识别所有语义错误，因此返回的正常状态始终是 `draft`，也就是待审阅草稿，而不是“诊断已确认”。

提示中要求不生成操作命令，同样不能成为绝对保证。即使模型把命令写进文本，当前程序也没有执行这些文本的入口。显示层仍应把内容当作不可信文本处理；后续接入工具时，更必须建立独立的授权与执行边界。

## 5.5 把失败设计成应用结果

“失败时返回一个错误”还不够。用户需要知道当前任务发生了什么，以及下一步应当补充材料、修正输入还是稍后重试。

示例使用四种外层状态，它们由应用产生，不直接照搬模型的自我评价：

| 状态 | 含义 | 典型处理 |
| --- | --- | --- |
| `draft` | 生成完整，报告通过程序校验 | 展示草稿与证据，等待人工审阅 |
| `needs_review` | 无证据，或模型明确报告材料不足 | 展示信息缺口，交给人工补充或判断 |
| `unavailable` | 调用、生成完整性或输出校验失败 | 告知暂时无法提供报告，保留原始材料入口 |
| `invalid_input` | 证据包不满足输入约定 | 要求调用方修正输入 |

`draft` 也需要人工审阅。`needs_review` 则进一步表明当前材料不足以支持正常草稿，不能把两者理解为“一个已确认、一个未确认”。

外层 `status` 与内层 `assessment` 的职责也不同：前者描述应用处理结果，后者保留模型对材料完整性的判断。模型可以返回 `insufficient_data`，但不能把整个应用标记成“故障已解决”。

### 没有材料与服务故障是不同的问题

当证据为空时，应用能够明确知道材料不足，不需要生成内容。返回结果可以是：

```json
{
  "status": "needs_review",
  "reason": "no_evidence",
  "prompt_version": "alert-report-v1"
}
```

如果调用超时，应用并不知道材料是否足够，只知道此次生成未能提供可接受的结果。它应该返回 `unavailable`，不能伪装成模型分析后的“证据不足”。

如果材料相互矛盾，情况又不同。它是一个需要内容理解的任务。我们会要求模型标记信息缺口，并用矛盾样例评价这个行为，但当前程序并没有实现通用矛盾检测器，不能承诺自动识别所有冲突。

### 不把失败文本包装成报告

当校验不通过时，示例不返回模型原始响应作为 `report`。如果产品直接把被拒绝的内容显示在正常报告区域，校验就失去了作用。

调试时可以在受控环境中保留必要的失败信息。真实服务还需要关联请求 ID、失败阶段和版本，按数据敏感程度控制日志内容与保留时间。本章示例只返回简短原因码，尚未实现持久化审计与生产日志系统。

## 5.6 运行配套示例

[配套目录](../examples/alert-assistant/README.md)包含一个只使用 Go 标准库的程序、教学输入、保存的报告响应和关键行为测试。模块声明的语言版本为 Go 1.22，本轮实际验证环境为 Go 1.27.1、macOS arm64；未声称已在全部兼容版本与操作系统上验证。

在仓库根目录执行：

```sh
cd examples/alert-assistant
go test ./...
go run .
```

程序默认读取 `fixtures/alert.json` 和 `fixtures/report.json`。输出外层包含：

```json
{
  "status": "draft",
  "reason": "review_required",
  "prompt_version": "alert-report-v1"
}
```

上面只展示结果元数据；实际输出还包含完整 `report` 对象。它整理错误率变化、发布时间关系与调查假设，并保留尚待确认的问题。

你也可以复制响应文件，将某项发现的引用改为 `E999`，再运行：

```sh
go run . -response /path/to/modified-report.json
```

`/path/to/modified-report.json` 是需要替换的本地文件路径。程序应返回 `unavailable`，原因为 `invalid_output`，且不包含 `report`。这说明输入与输出之间的引用约束已经生效。

命令行工具成功输出一个业务结果时，进程退出码为零，即使业务状态是 `unavailable`。文件读取或 JSON 输入解析错误则写入标准错误并以非零状态退出。集成这个教学命令时，应读取 JSON 状态，不能仅凭进程退出码判断报告是否可用。

### 哪些行为已经得到验证

配套测试覆盖的是业务边界，而不是标准库本身的实现：

- 无证据、重复证据 ID 和无效时间窗口不会进入模型调用。
- 有效结果仍以草稿返回，信息不足会进入人工补充路径。
- 未知引用、缺失引用与越出约定的结果类别会被拒绝。
- 超时错误、服务错误、截断、拒绝和不可接受的输出不会成为报告。
- 已取消的请求不会继续发起模型调用。

这些测试不会比较模型的分析文字，也不会给出任何模型准确率。在本地文件回放中观察到的运行时间，不是在线模型延迟；没有调用服务，也不能据此填写 Token 用量或调用成本。

## 5.7 为真实模型建立第一份评测集

接入真实模型后，需要从“程序正确处理响应”继续走向“生成内容值得使用”。最初的评测集可以很小，但每个样例都要说明它检验什么问题。

| 样例类别 | 输入变化 | 需要检查的行为 |
| --- | --- | --- |
| 常规材料 | 指标、发布与日志摘要齐全 | 保留关键事实，区分观察与假设 |
| 部分缺失 | 只有指标，没有日志和发布记录 | 不补造发布事件，说明调查缺口 |
| 材料冲突 | 两份同口径记录给出不同错误比例 | 指出冲突，不随意选一份当作确定事实 |
| 时间错位 | 日志来自前一天，告警发生在今天 | 识别材料关联不足，避免直接用于解释当前异常 |
| 指令污染 | 日志正文包含要求忽略任务的文字 | 保持任务边界，不把材料中的要求当作新指令 |
| 易误判的相关性 | 发布与异常接近，但缺少其他证据 | 保留假设，不宣称因果已确认 |

这张表是评测设计，不是已经跑出的模型结果。仓库目前提供常规材料与应用边界测试，表中的其他语义样例需要在真实模型实验中补充、执行与评审。

### 使用检查项而非唯一标准答案

开放式报告往往不存在唯一措辞。为每个样例写一篇标准答案，再逐字比较，可能会错误惩罚有效表达，也可能放过看起来相似但含义错误的输出。

更适合本案例的是行为检查项。例如，对常规材料要求：

1. 正确保留错误比例及比较窗口。
2. 不宣称所有请求失败。
3. 说明发布与异常只是目前观察到的时间关系。
4. 不虚构客户、地区或收入影响。
5. 给出与缺失材料有关的调查问题。

程序可以检查部分数值和引用，人需要判断语义与调查价值。初期应记录每个失败样例的具体原因；随着样例增长，再形成稳定的评分流程和评审一致性要求。

### 与一个简单基线比较

在调用模型之前，应用已经拥有证据包。因此，一个值得比较的基线是固定模板：按来源列出材料，并提示值班人员人工分析。它没有模型生成的调查假设，但流程简单、可预测。

模型方案应当证明自己的增量价值：是否减少阅读与整理时间，是否更容易发现缺口，是否保持事实准确。表达更流畅并不自动意味着更好。

进行比较时，向评审者提供相同输入对应的两份输出，尽量隐藏生成方式，并交换展示顺序。记录任务完成情况、关键错误与人工修订时间。样本很少时应保留逐条结果，不宜把一个百分比写成普遍结论。

### 分开统计不同阶段的指标

一个最小记录表可以包括输入版本、提示版本、模型标识、生成是否完整、契约是否通过、内容是否通过评审、耗时与供应商返回的用量。

“契约通过率”可以定义为：进入模型生成的请求中，完整生成且通过应用校验的次数占比。对于已经在输入阶段拒绝的请求，应单独统计，避免混入模型生成的分母。

同时还要计算任务级结果：所有符合业务条件的提交中，有多少最终产生了经审阅可用的报告。只报告前一个指标，会掩盖格式正确但内容无用的情况。

耗时至少区分模型调用耗时和应用端到端耗时。成本应使用实际用量与对应价格条件计算；如果数据未返回，就保留“未知”。当前离线示例不填报这些在线指标。

## 5.8 从回放程序接入真实服务

当应用边界验证通过后，可以实现一个满足 `Model` 接口的在线适配器。接入过程应保留当前业务校验，而不是因为模型支持结构化输出就移除它。

具体实现需要完成以下步骤：

1. 从运行环境读取凭证与模型配置，按照实际选定的官方接口组织请求。
2. 将 `Instructions` 与 `InputJSON` 分别映射到指令与输入位置；若支持结构化输出，提交完整报告 Schema。
3. 将 Context 传给真实网络请求，限制响应读取大小，并提取服务端结束原因。
4. 将完整文本与结束原因映射为 `Response`；鉴权、限流和连接失败等调用问题返回错误。
5. 记录模型标识、提示版本、请求 ID、耗时与可获得的用量，运行前述语义评测样例。

不要把 `SavedResponse` 的行为当作在线适配器模板：它忽略请求内容、直接读取文件，也没有真实生成状态。这是测试替身的职责，不是服务集成的职责。

本章保留这个接入点，是为了将供应商变化与应用设计分开。完成特定供应商的适配后，需要补充对应版本、运行说明与实际实验记录，才能声称应用已经通过在线验证。

## 本章小结

这个最小应用建立了输入、生成、校验与呈现之间的责任边界。模型负责整理材料，应用负责控制流程，评测与人工审阅负责判断报告是否有价值。

目前我们得到的是一个可运行的应用边界示例，以及一套可以继续检验真实模型的任务约定。它还不会主动查询更多证据，也不会执行运维操作。下一章将从这里出发，把指标、日志和发布记录查询封装为工具，同时明确每次外部调用的权限、错误和副作用。

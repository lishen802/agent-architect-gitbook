# 第 8 章：上下文预算分配与记忆写入检查

本目录用两个小程序演示第 8 章的两处控制点：为一次模型调用分配上下文预算并记录清单，以及在写入长期记忆之前做系统校验。所有数据都是教学构造；程序不调用模型、不联网、不读取生产数据。

## 文件与职责

| 文件 | 内容 |
| --- | --- |
| [context_budget.py](context_budget.py) | 材料信封、预算计算、按优先级选择材料、按固定顺序组装并输出清单 |
| [memory_policy.py](memory_policy.py) | 记忆写入前的系统校验、版本替换、读取过滤与按用户删除 |
| [scenario.json](scenario.json) | 告警助手第二轮追问时的 14 条候选材料与预算配置 |
| [demo.py](demo.py) | 对 `scenario.json` 运行分配器，打印上下文清单 |
| [manifest.json](manifest.json) | 本轮实际运行 `demo.py` 得到的清单 |
| [test_context_memory.py](test_context_memory.py) | 13 项关键行为测试 |

示例使用 Python 3.9 或更高版本的标准库，无第三方依赖。从仓库根目录执行：

```sh
python3 -B -m unittest discover -s examples/context-memory -v
python3 -B examples/context-memory/demo.py
```

预期结果：可用输入 24800，实际使用 16900；纳入 11 条材料，`X1` 因租户不符、`H2` 因历史类上限、`E5` 因超出剩余预算而未纳入。

## 预算规则

可用输入 = 窗口 − 输出预留 − 安全余量（窗口的固定比例）。指令与工具定义是固定项，标为 `required` 的材料是必需项，两者必须全部放下，否则返回 `needs_review` 且不组装任何上下文。其余材料按 `priority` 从小到大整条选择：超过本类上限记为 `kind_cap`，超过剩余预算记为 `over_budget`，然后继续尝试后面的材料。分配器从不截断一条材料的中间部分；需要缩小时，应在上游生成一条新的、带自身来源的压缩材料。

`tokens` 字段代表调用前用所选模型的计数接口得到的数。`estimate_tokens` 只是本地实验用的保守估计（每个汉字计 1，其他字符每 3 个计 1），不是任何模型的分词器，不能替代计数接口。

租户过滤在分配器里再做一次，是纵深防御的演示；真实系统应在查询时就按认证上下文过滤，不应让其他租户的材料进入候选列表。

## 记忆写入规则

`check_write` 返回 `accept`、`pending_review` 或 `reject`：

- 拒绝：缺字段、租户或用户范围与认证上下文不符、来源引用不存在、内容为空或超长、服务事实缺少有效期。
- 待审：来源是模型推断；处置经验未经人工确认；偏好不是用户本人陈述；内容像指令（如“以后……直接……”）。
- 接受：其余情况。

“像指令”的检测只是一项审阅信号，换个说法就可能绕过；它不能代替执行边界上的授权。`apply_write` 写入新版本，旧的可信版本标为 `superseded` 保留审计。`select_for_context` 只返回同租户、本人或团队范围、状态为可信且未过期的条目。`delete_subject` 只删除记忆存储中的条目，由它派生的摘要、索引和缓存需要调用方另外清除。

## 验证范围

测试覆盖：清单与正文数字一致；随机材料大小下预算从不超限、必需项始终在场；必需项放不下时返回待审且上下文为空；输入顺序打乱后清单不变，问题总在最后；其他租户材料在空间充足时也不进入；非法记录被拒绝；模型推断不能直接成为可信记忆；范围、来源与有效期检查；指令样式内容进入待审；版本替换与读取过滤；按用户删除全部版本。

它们验证的是应用规则，不度量任何模型在这些上下文上的回答质量。上下文策略的效果需要按[第 8 章](../../part-2/08-context-engineering.md) 8.8 节用任务集对照评测。

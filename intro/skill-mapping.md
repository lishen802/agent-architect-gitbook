# 导读：从后端架构师到智能体开发者

你可能已经能把一个业务需求拆成接口、数据模型、服务和消息流，却在面对“做一个智能体”时不知从哪里开始：应该直接调用模型，先建知识库，还是选择一个 Agent 框架？原来熟悉的设计步骤似乎没有消失，但新的名词让判断顺序变得模糊。

本书面向有后端开发经验的工程师与架构师。读者不必先成为模型训练专家，但应当熟悉接口、数据库、异常处理、测试与基本服务运行。我们的目标是让你面对一个没有在书中出现过的需求，也能提出有依据的初步方案。

## 本卷的交付目标

读完本卷，你应当能写出一页方案，说明任务目标、无需模型的基线、控制方式、信息来源、工具与权限、状态与失败、验收方法和资源预算。对于还不能确定的选择，应能提出最小验证实验。

一页方案不是上线许可证。它把“我觉得应该这样做”变成可以讨论、验证和修改的设计。第 2 章提供统一决策清单，此后的应用、场景和练习都沿用同一组问题。第一篇末尾的[设计速查](../part-1/design-handbook.md)把这些问题整理成参考架构、十种常用模式和八步构思流程，供做设计时随手查阅。

本书是丛书第一卷《智能体应用开发：方法与架构》。它保留必要的接口、状态和流程示意，用少量可运行示例说明边界；完整行业实战和特定框架操作另行成卷。第一卷的完成标准是形成判断能力，不是接触尽可能多的框架。

## 三条贯穿全书的线索

**可以沿用的经验。** 接口契约、权限、幂等、状态机、并发控制、监控与故障恢复仍然有用。模型参与流程后，并不会自动承担这些职责。你原来用来约束外部依赖的方法，可以成为新应用的基础。

**需要补充的能力。** 需要学习怎样组织给模型的信息、表达输出约定、判断开放式结果、选择检索证据，以及限制动态行动。除了程序能否正确执行，还要评价生成内容是否真正满足任务。

**需要调整的习惯。** 不能看到合法 JSON 就把内容当成正确事实，不能把模型解释当作独立证据，不能把一个成功演示当作稳定性结论，也不能因为需求包含“智能体”就省略不使用模型的备选方案。

这些线索不是后端知识与新名词的一一替换。单元测试继续存在，评测补充任务质量验证；数据库事务继续存在，人工审批不能替代原子性。书末的[后端概念对照表](../appendix/backend-concepts.md)同时列出迁移价值与类比失效的位置。

## 每章怎样帮助你做设计

每章开头先说明已有经验、新增问题和本章应产出的设计。正文围绕机制与取舍展开，末尾提供一道新需求题及参考思路。

参考思路不只有一种架构。它应解释当前条件下为什么优先考虑某个方案，为什么暂不选择另外几种，以及条件变化后如何调整。阅读时可以先写自己的答案，再检查有没有遗漏关键约束，而不是背诵推荐组件。

场景篇采用六项固定结构：需求特征、候选架构与选择依据、难点、常见坑、评测验收、安全合规。每章至少改变一次需求条件，展示方案如何随之改变。场景内容讨论设计方法，不冒充已经上线的成功案例。

## 先明确判断，再增加自主性

“使用模型”和“让模型决定下一步”是不同的选择。一个有价值的应用可能只是受控流程中的一次生成，也可能需要固定工作流，或在局部采用动态调查。

检索与审批又是另外的维度。固定工作流可以检索，也可以需要审批；智能体可能只使用当前材料；只读查询仍可能涉及敏感数据。不要把这些能力排成一条必然升级的阶梯。

本书会先教你判断任务和验收，再逐步增加能力。涉及框架、供应商接口与法规的内容注明核验范围，避免把变化较快的细节当作永恒结论。

## 用一个陌生需求检验学习结果

读完样章后，拿一项未出现过的需求，完成第 2 章的一页方案。检查自己能否：指出不需要模型的部分；列出至少两个候选方案；说明证据与动作边界；设计失败出口；给出判断结果是否合格的方法；写出会改变当前选择的条件。

如果只能画出“用户—大模型—工具”，还没有完成设计。如果能解释哪些组件暂时不需要，以及什么证据会使你改变方案，就已经开始形成可迁移的工程判断。
